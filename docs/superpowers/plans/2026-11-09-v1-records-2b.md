# Sub-project 2b: changing authorised work, closure and deadline review — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Authorised work changes only through authorisation under a configurable count of distinct approvers; projects account for every open item when they close, and outstanding work gets new authorised dates before it restarts.

**Architecture:** A new `src/changes/` module owns the approval policy, change requests, versions and approvals, with one handler per request kind that validates terms and applies the change in the transaction of the completing approval. 2a's authorise routes become `authorise_proposal` requests. Closure and deadline review are services in the same module that create requests and gate the existing lifecycle transition.

**Tech Stack:** TypeScript, NestJS, PostgreSQL 16 (plain SQL migrations), React + Vite, `node:test`. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-11-09-v1-records-2b-design.md`

## Global Constraints

- Approval counts are 1, 2 or 3; organisation default 1; projects may override only when the Administrator allows (`projects_may_override`, default false).
- A distinct person counts once per request version; Audit/Oversight holders never approve; approving one's own request is allowed.
- Eligible approvers: active Owner or Sponsor memberships in the request's project.
- One open (pending) change request per record; one pending `authorise_proposal` per proposal.
- A pending request never changes its target; the completing approval applies the change in its own transaction under the target's row lock.
- Exact copy: `This task already has a change waiting for authorisation.` / `This decision already has a change waiting for authorisation.` / `This risk already has a change waiting for authorisation.`; `Not enough approvers: needs N, the project has M.`; `Change at least one of the wording, the assignee or the due date.`; `A completed or cancelled task cannot be changed; propose a follow-up task instead.`; `Only the assignee, the Project Manager, a Deputy, an Owner or a Sponsor can propose changes to this task.`; `This task needs a new authorised due date first.`
- Project states per kind: `authorise_proposal` Planned/Active; `amend_task`, `cancel_task`, `supersede_decision`, `withdraw_decision` Active (closure-batch `cancel_task` also Deferred); `deadline_review`, `reconcile_completion` Deferred/Closed/Active; `risk_handover` offered while origin Active/Deferred, approved while the receiving project is Active.
- Dates are UTC+8 calendar days (`todayUtc8`); "in the past" means before today UTC+8.
- Every write is audited with `writeAudit`; history tables are append-only.
- Count 1 keeps 2a's authorise behaviour: 201 with the record; count 2–3 answers 202 with the request.
- Test accounts only: `*@example.org`, `*@kainow.test`.

## Review Focus

1. Two approvers completing the count at the same moment — the change is applied exactly once and both get 200 (Task 4).
2. A request approved after its target changed underneath it (task completed, decision superseded, assignee's membership expired) — refused with the re-check reason, request stays pending (Task 4/5).
3. A policy change with pending requests, choosing Restart — every affected request's approvals are cleared and its count re-captured; Keep leaves them untouched (Task 3).
4. Closing while a closure-batch cancellation or a risk hand-over is still pending — Close refused naming the pending items (Task 7).
5. A task under a deadline review mark whose parent's review is still pending — its own approved date lets it start; the parent's completion rule still applies (Task 9).
