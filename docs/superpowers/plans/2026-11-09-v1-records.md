# Sub-project 2a: Authorised Records — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Authorising a proposal creates one task (with optional subtasks), decision, question or risk, and those records follow their accepted lifecycles.

**Architecture:** Pure transition tables for tasks, questions and risks (`app/src/records/*.ts`) decide who may do what in which state; a `RecordsService` creates records inside the same transaction that approves the proposal, so one proposal yields one record; lifecycle routes go through `ProjectAccess` and the pure tables. The existing review "approve" stays as the first half of authorising, so items approved without a record are exactly the "approved before records existed" case.

**Tech Stack:** TypeScript, NestJS, PostgreSQL 16 (plain SQL migrations), React + Vite, `node:test`.

**Spec:** `docs/superpowers/specs/2026-11-09-v1-records-design.md`

## Global Constraints

- Dates `YYYY-MM-DD`, UTC+8 (`todayUtc8`); indicators worked out on read.
- Errors: 404 outside the project; 403 with the reason; 409 rule/state conflict; 400 bad input.
- History tables append-only via `kainow_append_only()`.
- Fixed copy: "A task needs one assignee and a due date before it can be authorised."; "Subtasks go at most two levels deep."; "Finish the subtasks first, or record an override."; "The assignee must be an Active member to start this task."; "Answered is not Resolved: the requester, Project Manager or a Deputy confirms the answer."; "Human proposal — no discussion source"; "Approved before records existed".
- Authorising: Owner or Sponsor; project Planned or Active; refused while a required role is missing (existing `MISSING_ACCOUNTABILITY`).
- Task operations need project Active; nothing changes on Deferred/Closed; grant holders read only.
- Severity values `low`, `medium`, `high`, `critical`.

## Review Focus

1. Two Authorise clicks on one proposal (same or different reviewers, concurrently) create exactly one record or task tree; the second returns it. → Task 3 test "one record however many clicks".
2. Completing a parent whose subtask is still open is refused unless a PM/Deputy override reason is given; the override leaves the subtask open. → Task 5 test "parent completion".
3. Reopening a second-level subtask whose parent and grandparent are Completed reopens all three in one action with three history rows. → Task 5 test "reopening reopens completed ancestors".
4. An assignee invited by email: the task shows Awaiting Membership (with the invitation state) and cannot be started by anyone until the invitee holds an Active membership; after acceptance it can. → Task 3 test "invite gives Awaiting Membership until acceptance" and Task 5 test "start needs an Active assignee".
5. Overdue at the UTC+8 boundary: due 2026-11-09 is not overdue at 2026-11-09T15:59:59Z and is at 2026-11-09T16:00:00Z. → Task 2 test.

### Task 2: Pure rules

**Files:** Create `app/src/records/tasks.ts`, `app/src/records/lifecycles.ts`; Tests `app/src/records/tasks.test.ts`, `app/src/records/lifecycles.test.ts`.

**Interfaces — produces:**
- `type TaskStatus = 'not_started' | 'in_progress' | 'blocked' | 'completed' | 'cancelled'`; `type TaskAction = 'start' | 'block' | 'unblock' | 'complete' | 'reopen'`.
- `taskTransition(input: { action: TaskAction; status: TaskStatus; actor: { isAssignee: boolean; roles: ProjectRole[] }; projectStatus: ProjectStatus; assigneeActive: boolean; note: string | null }): { allowed: true; to: TaskStatus } | { allowed: false; reason: string }` — the spec's task table; `note` is the reason/resolution/completion note (required for block, unblock, complete, reopen). Refusals: not Active → "Tasks change only while the project is Active."; actor → "Only the assignee, the Project Manager or a Deputy can do this." (reopen: "Only the Project Manager or a Deputy can reopen a task."); start/complete by the assignee themself without an Active membership, or start by anyone while the assignee is not Active → "The assignee must be an Active member to start this task." (complete by PM/Deputy is allowed); missing note → "A note is required."; wrong state → "That change is not possible from <Status label>.".
- `parentMayComplete(children: TaskStatus[], overrideReason: string | null, actorRoles: ProjectRole[]): { allowed: true; override: boolean } | { allowed: false; reason: string }` — every child completed/cancelled, or a non-empty override by pm/deputy_pm; else "Finish the subtasks first, or record an override.".
- `ancestorsToReopen(chain: Array<{ id: string; status: TaskStatus }>): string[]` — given the task's ancestors (parent first), the ids of completed ones, stopping at the first that is not completed.
- `taskIndicators(input: { status: TaskStatus; dueOn: string; parentDueOn: string | null; assigneeActive: boolean; invitationStatus: 'invited' | 'declined' | 'expired' | 'revoked' | 'accepted' | null; today: string }): { overdue: boolean; awaitingMembership: boolean; invitation: string | null; dueAfterParent: boolean }`.
- `lifecycles.ts`: `questionTransition({ action: 'answer' | 'resolve' | 'reopen' | 'withdraw'; status; actor: { isRequester: boolean; roles: ProjectRole[]; active: boolean }; projectStatus; note })` and `riskTransition({ action: 'mitigate' | 'update' | 'accept' | 'resolve' | 'reopen'; status; actor: { isResponsible: boolean; roles: ProjectRole[] }; projectStatus; note; responsibleSet: boolean; reviewOnSet: boolean })`, both returning `{ allowed: true; to } | { allowed: false; reason }` per the spec's tables. Resolve from `open` → "Answered is not Resolved: the requester, Project Manager or a Deputy confirms the answer." (questions need an answer first: resolve only from `answered`). Accept without responsible person or review date → "Accepting a risk needs a responsible person and a review date.". All question and risk changes need the project Active, as tasks do.

- Task rules: `assigneeId` must have a Scheduled or Active membership in the project, or `inviteEmail` must be eligible; `dueOn` required and a calendar date — else 400 "A task needs one assignee and a due date before it can be authorised."; each subtask needs the same; subtasks get `depth = 1`, `parent_id` = the task; one `task_events` row `authorised` per created task.
