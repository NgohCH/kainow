# Kainow V1.0 — Remaining Design and Verification Register

**Version:** 1.0  
**Date:** 6 November 2026  
**Edition:** Product handover; accepted requirements consolidated, not evidence of implementation or delivery acceptance.  
**Scope:** Product only; development method and environment setup excluded.

## 1. What remains and what does not

The V1.0 product scope and accepted decisions D01–D70/O01–O17 are recorded. This register makes the remaining design, organisational setup and verification work explicit. It is not an environment plan, coding packet queue or authority to introduce new features.

“Accepted requirement” is different from “designed”, “implemented” and “verified”. No implementation, security, usability, performance, licensing-file or deployment checks were executed for this handover. A complete handover gives the developer the requirements and exposes the work still needed; it cannot substitute for these checks.

**Types:** Design = developer proposes a concrete solution consistent with scope; Setup = organisation provides actual values/people; Clarification = accepted documents do not settle a material edge case; Verification = evidence required against the resulting product. Do not label a newly invented product policy as a technical detail.

**Builder notes for sub-project 10a.** These refine the decisions without changing them; the D-rows stay as the Product Owner approved them.

- **Backup folder variable (Compose).** `KAINOW_BACKUP_DIR` is a long-syntax bind mount with `create_host_path: false` and no `:?` check, so a missing or unset folder fails only the `ops` runs; every other `docker compose` command on an existing installation is unaffected. INSTALL.md explains the failure.
- **Image target.** `x-kainow` keeps `target: runtime`, and the `ops` image stage (`FROM runtime AS ops`) is the last stage in the Dockerfile, so a build without `--target` would produce the `ops` image. Compose names the target for every service.
- **Sets without a database row (D110).** A backup set folder that has `backup.json` but no `backup_runs` row (for example after restoring an older database) is a complete, succeeded set. Its kind and finish time come from `backup.json`, it follows normal retention and counts as a keeper. A set is incomplete only when its name ends `-incomplete`, or it has neither a row nor `backup.json`.
- **First day (D111).** A new installation with no backup yet starts the "target exceeded" episode only once the organisation has been registered for more than 24 hours, so a fresh install stays quiet for its first day. An interrupted run also sends the `backup_failed` notice, because the dead command could not. A run that finishes after being marked interrupted may still record success (its set is verified), without a second notice.
- **Refused drills (D112).** A drill that is refused before it starts (protective mode on, no backup set, wrong key, key missing, another run in progress) records nothing in Kainow, like the lock refusal. The cron log carries the text, and the Operations page's "Last drill" age still shows a missed drill.
- **Drill name.** The temporary database is named from the last 12 hex characters of the run id (the first characters of a time-ordered id repeat within about a minute).
- **Restore (D112).** `pg_restore` runs in one transaction. The restore checks space itself before starting: the set's database size x 1.2 + the default 5 GB floor + 2 GB (there is no live database to measure and an empty target has no settings), then polls free space every 30 seconds while restoring. The post-restore steps (sessions and sign-in codes removed, queued emails marked not sent, queued work ended with "Not run — restored from backup", pg-boss jobs cancelled, protective mode on) run in a separate transaction after `pg_restore` commits, because `pg_restore` is its own process. If a restore is interrupted, the operator must drop and recreate the target database empty before starting Kainow; the restore refuses a database that already holds tables, and its messages say so.
- **Quarantine cleaning (D112).** A restore does not end quarantine cleaning: it is local, repeatable and removes a reported secret, so ending it would leave the secret in place. Its queued job is cancelled with the others, and cleaning resumes after an Administrator chooses Resume.
- **Administrator notices.** Operations notices are written as an in-app notice (email switched off on that row) plus one queued email per Administrator in the email outbox. The resume checks are also served by `GET admin/operations/resume-checks`, so the page can show pass or fail before the Administrator confirms.
- **Analytics.** The analytics Operations panel's growth follows the chosen period; the Operations page overview always shows 30 days.
- **Backup size.** The `database_bytes` of a run is the size of the encrypted dump, shown on the Operations page as "Backup size (encrypted)", not the live database's size.
- **No command timeouts yet.** `pg_dump` and `pg_restore` have no timeout. A hung tool keeps the backup lock until the container is stopped; the sweep marks a backup run interrupted after 6 hours but does not stop the tool.
- **Sealed values.** The drill's "protected key opens a sealed value" check covers the AI connection key, the quarantine original and the storage connection secret (opened with its binding, through `storageSecretReadable`; the plain value is dropped at once).
- **Job-queue archive.** pg-boss expires its own archive after a fixed 7 days (pg-boss 12.38.1); the diagnostics setting does not change it.
- **Source area.** Built with sub-project 9 joined: the backup copies `stored` source files (R25: files flagged Missing or Changed, or being moved, are listed not copied and counted in the run's note; never a failure), reads the list inside the export snapshot (R26), stops copying 4 hours after the run started (R27; the next run copies the rest), and needs the protected key in `ops` once a source area is approved. While none is approved (and no file is stored) the manifest says "Source area: not in use" and uploaded originals travel in the database part. `source_area` reading: used and quota as the Storage page gets them (the source area's last destination check), never a provider call from `ops`. `restore-source-files` uploads a missing file into the approved source area at its version folder and switches the reference with a `stored_file_moves` row, as the relocation routine does (that routine itself copies from the old item, which is gone here). **Not verified against a real tenant** (fake Graph server only).
- **Backup key change and the file store (R30).** The store is kept per key: `files/<key id>/<2>/<sha>.enc`. A new key copies every file into its own folder and never overwrites an earlier key's, so earlier sets stay readable, source files included, with the earlier key (spec 5.6). Expiry reads the mounted key's manifests to remove that key's unlisted files, and removes an earlier key's whole folder once no remaining set was made with it (a set's key id is in its plain backup.json); it cannot read earlier-key manifests, so it leaves their folders whole until then.
- **Lost source files during a backup (R29).** A download that finds the item gone flags the file Missing through sub-project 9's `flagStoredFile` (its notice follows) and the run succeeds with the "already flagged" note. Any other download failure fails the run `source_files_failed`, naming the stored-file ids in the output and the failure detail; `files_not_copied` on a failed run is that same count.
- **Storage files after a restore.** The restore fails stored files left `pending` or `storing` (failure code `restored_from_backup`, worded "Not run — restored from backup") and puts `relocating` files back to `stored` at their confirmed place. After Resume, sub-project 9's daily source task stores failed source versions again; an output shows "Filing failed — Not run — restored from backup" with Try again; the daily relocation task moves files again.
- **Storage queue in protective mode (R28).** The worker's storage job handler holds every fetched job while protective mode is on (sent again a minute later, no attempt counted), as the AI queue does; the outbox and daily ticks already paused.
- **Low-space check size (D114, spec 7.4).** The spec's example 3 GB file system is smaller than the default 5 GB safe floor, so Kainow would be in protective mode from the start. `docs/operations/verify-low-space.md` uses 12 GB, so the default floor is what is tested; a smaller file system needs a lower floor and then tests that lower value instead.
